# wedgie

Jiro on a [wedgie](https://wedgie.dev): jiro-core as a MicroPython native module, `jiro_core.mpy`, and the apps that run it (README §2, §3). The wedgie keeps its own firmware (0.3.76, and 0.3.77 since round E1's fourth try, both MicroPython 1.29.0), so the module is built for that MicroPython and checked on its qemu port before it reaches a device.

| Path | What |
|---|---|
| `natmod/rust/` | `jiro-natmod`: jiro-core behind an `extern "C"` interface, a `staticlib` for `thumbv6m-none-eabi`, position-independent, with no `.data` and no `.bss`. Its own Cargo workspace. |
| `natmod/glue/` | The C glue (`jiro.c`), the stack switch (`call_on_stack.S`), the interface (`jiro_api.h`) and the Makefile that links `jiro_core.mpy` |
| `scripts/` | The builds, the qemu vector run, the app's qemu play test, the stand-in for the wedgie firmware's key IRQ that the play test runs with (`irqsim/`), and the checks of `mpy_ld`'s rules, of the module's header, of the frames of the app's tick and of the app limits |
| `check/` | The check app: it replays every golden vector through the module on a wedgie and shows PASS or FAIL per vector |
| `app/` | Jiro-ikusu, the Training app: the 16 levels, offline, at 15 Hz, with local best scores (README §8.1) |

## Building

```bash
bash scripts/bootstrap.sh wedgie          # arm-none-eabi-gcc, qemu-system-arm, MicroPython v1.29.0, pyelftools 0.32
bash wedgie/scripts/build-qemu.sh         # mpy-cross and the qemu firmware; prints the firmware's path
make -C wedgie/natmod/glue                # jiro_core.mpy, then the mpy_ld rules and header checks
python3 -I wedgie/scripts/qemu_natmod_vectors.py <firmware.elf> wedgie/natmod/glue/jiro_core.mpy . --all
bash wedgie/scripts/build-check.sh        # the check app in wedgie/check/, and its app limits
bash wedgie/scripts/build-app.sh          # the Training app in wedgie/app/, its tick's frames and its app limits
cargo build -p jiro-tools --locked        # native replay, which the play test checks against
python3 -I wedgie/scripts/qemu_app_check.py <firmware.elf> wedgie/app 137760
bash wedgie/scripts/build-qemu.sh irqsim  # the same firmware with irqsim, a stand-in for the wedgie firmware's key IRQ
python3 -I wedgie/scripts/qemu_app_check.py <irqsim firmware.elf> wedgie/app 137760 --hard-irq
python3 -I wedgie/scripts/qemu_app_check.py <firmware.elf> wedgie/app 113568 50        # the heap a power-up with the WEDGIE drive leaves
python3 -I wedgie/scripts/qemu_app_check.py <firmware.elf> wedgie/app 100000 --screen  # the screen, checked after every tick
```

The bootstrap puts MicroPython and pyelftools in `~/.cache/jiro-wedgie` (`JIRO_WEDGIE_HOME` moves it); docs/TOOLING.md records the versions. Run the qemu check under a timeout, as CI does: a module that hard-faults hangs qemu instead of failing. For a vector that fails, it also prints the first tick whose state hash differs from the committed trace (README §6.6), within the first 1,024 ticks: a whole trace does not fit beside the stack in the qemu port's heap.

- **Link order.** For armv6m, MicroPython v1.29.0's `mpy_ld` builds the module's entry trampoline from `mpy_init`'s offset in its own section, before it lays out the sections. That is right only when the object defining `mpy_init` is linked first. The spike's first build linked the Rust object first: its trampoline jumped into the middle of `jiro_recorder_step`, and the module froze a wedgie on its splash screen and hard-faulted on qemu. The Makefile links the glue's objects first.
- **Size.** The module is 18,588 bytes, of which 18,352 bytes of code, and takes 19,176 bytes of heap once imported (M3.8's, without the renderer's exports, was 15,890 and 16,460). `natmod/rust` builds at `opt-level = "s"`, its smallest: at M3.8, 14,356 bytes of Rust code, against 15,474 at `"z"` and 18,296 at `2`; 15,628 bytes now.
- **Reproducible in one directory.** Clean builds of a commit in the same directory agree, but a build in another directory can differ by about 100 bytes, of the same size (round E1's first build: `5867fff8…` in CI, `092c5a7f…` in a worktree), so the sha256 that names a module is CI's. CI prints the size and sha256 of its own build between `=== BEGIN jiro_core.mpy ===` and `=== END jiro_core.mpy ===`.
- **CI** (`wedgie` job of `.github/workflows/ci.yml`) runs these steps and uploads `wedgie/check/` and `wedgie/app/`, each with the module, as the `wedgie-check` and `wedgie-app` artifacts, kept 90 days.
- **qemu's clock.** The qemu port's ticks assume a 25 MHz SysTick, which qemu's nRF51 clocks at 16 MHz, so one microsecond the port measures is 1,562.5 instructions under `-icount shift=0` (the vector run) and 195.3 under `shift=3` (the play test): measured with an inline-assembler loop of known length. A wedgie runs 125 instructions per microsecond at one instruction per cycle. The port's heap is 236 KB, which holds the play test's files, the screen buffer and a wedgie's free RAM.

## The module's interface

`jiro_core` exports `rules_version()`, `recorder_size()`, `shadow_size()`, `start(recorder, level, mode, run_nonce, level_index, stack)`, `step(recorder, mask, stack)`, `journal(recorder[, start[, end]])`, `journal_equals(recorder, buffer)`, `state_hash(recorder, stack)` and `replay(level, journal, weight_bp, stack[, trace])`, and for the renderer `status(recorder, out)`, `score(recorder, weight_bp)`, `paint(recorder, shadow, frame, colors, rect[, full])` and `restore(recorder, frame, colors, x, y, width, height)`; `natmod/glue/jiro.c` documents the return values. A call whose buffers overlap, or a `restore` with a negative cell, raises `ValueError`. The caller owns all memory: a `bytearray` for the stack, of at least 24 KB for `start`, `step` and `state_hash` and 48 KB for `replay`, one of `recorder_size()` bytes for the Recorder and, to paint, one of `shadow_size()` bytes for the shadow of jiro-shell's dirty-cell diff.

- **The recorder buffer** holds a marker word, then the Recorder. `start` clears the marker, and writes it after the Recorder only when it succeeds; every other call that takes the buffer raises `ValueError` without it. So a buffer that no successful `start` wrote is never read as a Recorder. The marker does not guard against Python code writing into a started buffer: the app never touches it.
- **The renderer's exports** read the Recorder only. `status` writes 23 u16 fields: the end reason, ticks, time limit, lives, shield, invulnerability, cutting, claim and target, and the player's, the boss's and the three minions' cells (`natmod/rust/src/lib.rs`, `jiro_status`, which checks at compile time that they make the 23; the glue takes the count, and the framebuffer's size, from it). `score` is the ended level's score, with the core's `level_score`. `paint` runs jiro-shell's dirty-cell diff (`Shadow`, which the browser's `DirtyCells` uses too) and paints the changed cells, or with `full` every cell, into the wedgie's 4-bit framebuffer, returning their bounding rectangle; `restore` repaints a rectangle of cells from the grid, under an entity that moved. They run on the C stack, in frames of at most 204 bytes.

## Stack and RAM

- **Stack.** The rp2 port gives C code an 8 KB stack, so `start`, `step`, `state_hash` and `replay` run on a stack the app allocates: `call_on_stack.S` runs them on the Cortex-M0's process stack, set to the buffer's top, and keeps the main stack, the C stack, where it was. The glue requires 24 KB for the first three and 48 KB for `replay`. `start` builds the Recorder and its game in the recorder buffer, field by field (`Recorder::new_in` and `Game::new_in`, plan M3.10), so its stack holds only the level start's grid while validity is checked; `replay` builds its game on the stack with `Game::new`, as the referees do, whose code stays as it is. So the Training app allocates 24 KB and the check app, which replays, 48 KB. The qemu port's 8 KB stack size is a soft limit the VM checks, not a physical stack: the qemu run checks that the core stays on its buffer and fits it, and the wedgie run is the real check of the rp2 port. The qemu run measures the peaks over all 75 vectors: `start` 19,404 bytes and `step` 344, of the Training app's 24,576, and `replay` 46,820, of the check app's 49,152. Exception handlers always run on the main stack, so an interrupt during the core puts only its 32-byte exception frame on the buffer, well within the 5.1 KB above `start`'s peak and the 2.3 KB above `replay`'s. Round E1's third try froze a wedgie because the stack switch moved the main stack instead: the wedgie firmware's hard key IRQ (`power.py`, `Pin.irq(_touch, Pin.IRQ_FALLING, hard=True)`) then ran its Python callback on the buffer, where MicroPython's stack check failed, and printing that failure escaped the IRQ handler with the garbage collector and the scheduler locked (`reports/wedgie-2026-11-02.md`). A panic in the core goes back to the main stack before it raises. Before M3.10 the stack was 64 KB: `start` peaked at 62,784 bytes, 40.6 KB of it the module's own frame, which held copies of the Recorder, and 21.2 KB `Game::new`'s.
- **RAM.** The wedgie reported 137,760 bytes free with no app, and 115,344 during a `wedgie.py debug` job (spike, [PR #42](https://github.com/detychey/jiro-ikusu/pull/42)). An app needs, in large blocks, its stack (24 KB in the Training app), the 18,568-byte recorder buffer and the module's 18.6 KB: 61.7 KB. A power-up also starts the wedgie's USB drive, which leaves 113,568 bytes free with a largest block of 95,946 (round E1's fifth try): the 102 KB that the 64 KB stack made did not fit there, which reopened M3.10. So an app allocates the stack and the Recorder first, while the heap is whole, then imports `jiro_core`; ships its code precompiled with `mpy-cross`, so that no parse tree is scattered over the heap; and reads one level or vector at a time.
- **The check app** holds at most one vector at a time: up to 8,172 bytes of journal read from its file, which `journal_equals` compares with the Recorder's in place. On qemu, with the heap filled to leave a given amount free and M3.8's 64 KB stack, 16 KB more than its stack now, it passed with 137,760 bytes free in one block or with four 4 KB holes, down to 121,000 in one block and 120,000 with eight 1 KB holes, and failed with a MemoryError (an exception, not a freeze) at 120,000 in one block and 117,000 with the holes. The spike's smaller app, which held at most 5 KB per vector, passed down to 113,792 bytes free.
- **The Training app** allocates, in `jiro.py`, the stack, the recorder buffer, the 3,600-byte shadow and the 472-byte level buffer, and reads the bests; then imports `jiro_core`, opens the level file, which it keeps open, and imports `jiro_app.mpy` (6.0 KB), which reads the level file's index and makes room in the bests for a key per level (small ints, deleted again: MicroPython's dict keeps its table), so that a new best never makes the dict grow when a level ends. After that it allocates nothing sizable: a level start seeks and reads into the level buffer, a tick allocates nothing on the heap (the play test locks the heap over each tick's sample, step and drawing), and the summary's strings are small. Round E1's second try failed on a wedgie at the first level start with "memory allocation failed, allocating 1148 bytes": that build opened the level file there, and a file on the wedgie's littlefs is a 1,148-byte object (a 124-byte object and a 1,024-byte cache, MicroPython 1.29.0's rp2 port mounting it with `progsize=256`), more than the largest free block left after start. `save.store`, which opens such a file to write the bests, gets the core's stack's 24 KB block, idle between levels, which the app frees for it and takes back: nothing allocated in between stays alive, the store being a call of its own so that no live frame keeps a pointer to a caught exception (the garbage collector scans the stack conservatively), and if the block cannot be taken back the app raises a `RuntimeError` that says so. The app prints the free heap and its largest block at each stage over USB. In the play test at 137,760 bytes free, with 32 small holes, about 58.2 KB stay free after start, with a largest free block of about 10.7 KB, and on a heap like the one a power-up leaves with the USB drive, 113,568 bytes free with 17.8 KB of it in 50 to 64 small holes, about 33 KB; with every block over 1 KB then filled it plays two levels, and with every block over 256 bytes too. With the 64 KB stack about 17.1 KB stayed free at 137,760 bytes (`reports/wedgie-2026-11-02.md` has each stage). The e6198d3 build fails the play test at its first level start, as on the wedgie. M3.10's smaller stack followed round E1's fifth try, which a power-up with the USB drive stopped at the module's import (above).
- **Time.** On qemu's instruction count, replaying the 75 vectors takes about 19 billion instructions, the worst vector 572 million (M3.8 read qemu's microseconds as 1,000 instructions and gave 12.1 billion and 386 million; see qemu's clock above). At 125 MHz that is about 150 s, and the Recorder pass about as much again, so the check app runs for about 5 minutes. During a long replay the VM runs no scheduled tasks, so USB output stalls; the screen shows which vector runs.

## The check app

`check/` is a wedgie app (`mod` `jiro`, entry `run`). `jiro.py` allocates the core's stack and Recorder, imports `jiro_core`, then `jiro_check.mpy`, compiled from `check/jiro_check.py`. It reads `jiro_vectors.bin`, which `scripts/make_check_vectors.py` writes from every vector of `vectors/game/` and `vectors/levels/`, one record at a time. For each vector it checks replay's code, the Outcome, the tick count, traceKeccak and the last state hash; for a vector replay accepts, it plays the journal's inputs through the Recorder and checks its end reason, journal and final state hash. Before each vector it shows "vector i of 75" on the screen. It prints each result over USB, then shows PASS or FAIL per vector, eight to a page, as `ok 12 ture-split-boss-left`: the vector's number and the end of its name; green turns the page. The qemu run uses the same `read_case` and `check` on records of the same encoder.

`wedgie/scripts/check_app_limits.py` checks the wedgie's app limits on the files `wedgie.json` lists: at most 30 files and 256 KB, every name starting with the `mod`. The check app has 4 files and 231,499 bytes, the Training app 4 files and 35,761.

## The Training app: Jiro-ikusu

`app/` is a wedgie app (`mod` `jiro`, entry `run`, named Jiro-ikusu). `jiro.py` allocates the core's stack, the recorder buffer and the shadow, imports `jiro_core`, then `jiro_app.mpy`, compiled from `app/jiro_app.py`. `jiro_levels.bin`, which `scripts/make_app_levels.py` writes at build time, holds the 16 levels of `levels/` with the weights of `seasons/calibration-1.json`, in slot order. The app checks that the core runs the calibration's rules version, and, when it starts a level, that the level id in the journal the core began equals the calibration's.

- **Level select,** outside play and never journaled: the joystick picks one of the 16 levels, green plays it. It shows the level's name and best score. The app measures the free heap and its largest free block at each stage, `run` before the app allocates, `buf` after `jiro.py`'s buffers, `imp` after the imports, `lcd` after the screen, `app` after the app's start, `sel` at this level select and `lvl` at the last level start, and prints them over USB; until the shelf version (below) the level select showed them too.
- **Level start:** a fresh run nonce from `os.urandom(32)` (README §6.3 allows any in Training; not the firmware's `wedgie.rand`, whose first call probes the I2C bus for a secure element and keeps the drivers it imports, about 13 KB of the heap; Training plays at `levelIndex` 0, as in the browser), then the field with a brief overlay of the level's name, target and lives, for 1.5 s before tick 0.
- **The tick,** every 66,666⅔ µs on an absolute schedule: tick k is due at t0 + ⌊k × 10⁶ / 15⌋ µs, kept as a running due time that advances by 66,666 or 66,667 µs, so `ticks_add`'s delta stays small however long a level is. A late tick runs as soon as it can, and the next stays on its own due time: no tick is skipped or stepped twice. A due time is never more than one tick ahead, so one that `ticks_diff` reads further ahead is more than 2²⁹ µs late, past its range, and runs at once: the app never sleeps for minutes on a misread due time. Each tick samples the controls once into the README §6.1 mask, held or pressed since the last sample, with D8's mapping (joystick, A green, B and X grey); Y (red) and the joystick press are never in it. Then the core's Recorder steps with it, and the app repaints: `restore` under the entities' old cells, `paint` for the cells that changed, the boss, the minions and the player on top, and `show_rect` for each entity's old and new cells and for the changed cells' rectangle, or, when that rectangle is 128 pixels wide or more, `show(y0, y1)` for its rows at full width: a `show_rect` row costs about 45 µs plus 0.26 µs a pixel and a full-width row about 75 µs (wedgie.dev/code.md), and the firmware converts full-width rows in chunks and allocates nothing for them. A capture of most of the field still takes one tick past its due time on a wedgie (round E1's sixth try: a draw of 85.8 ms with the narrower push). Every 8 ticks, after a tick whose work took under 25 ms, the app runs a collection, which takes up to 27.5 ms on a wedgie: the firmware's `show_rect` leaves garbage each tick, and the collections it would otherwise trigger landed inside heavy ticks (round E1: 3 overruns, then none). That repainting is one call with few locals, since MicroPython puts a call's frame of more than 11 words on the heap, a first-fit search that a fragmented heap makes slow: it is the tick's only such frame. `scripts/check_app_frames.py`, which the app's build runs, reads the frames of the compiled app and fails if another of the tick's calls outgrows the C stack, or the repainting's frame its 7 heap blocks; the play test cannot see that, since under its locked heap such a frame goes to the C stack. The colors are the browser's (`web/src/render.ts`), each the nearest of the screen's 16, but the boss's: its magenta comes out as the trail's red, so the boss is yellow. The player is drawn 6 pixels wide, a pixel larger than its cell on each side, in a black ring a pixel wider, so it stands out on the 4-pixel trail it cuts, on the claimed area and on the borders (round E1: a 4-pixel white dot was hard to see on the trail); its old cell and the cells around it are restored.
- **Between levels:** the summary screen comes first, then the USB output, which can block for 500 ms a print when a host holds the port open without reading it, so the journal's lines stop at the first print that takes over 100 ms; presses made in the level's last moments and the first 0.5 s are discarded, so they do not skip it. It shows the end reason, the claim, the score (the core's, with the calibration's weight), the lives and ticks, and the best. The level's timing, the worst step, the worst draw, the worst tick and the overruns (ticks that ended after the next tick was due), goes to USB; the end screen showed it too until the shelf version, which keeps test figures off the players' screens (owner, 2026-11-09). Green goes back to the level select, on the next level after a clear; after a clear of the last level, a screen says "Congrats! visit jiro-ikusu.win" first, and green there goes to level 1.
- **Over USB** it prints the free heap and the largest free block at each of those stages, and after each level its end, claim, ticks, lives, score, timing and journal, in hex, which `jiro-tools replay` replays.
- **Best scores** are kept per level in the save `bests` (`/saves/jiro/`, which survives reinstalls), keyed by the rules version, the level id and the weight, as the browser's Training page keys them. If `save.store` fails, a full flash for instance, the summary says the best was not saved, and the app plays on.

**The play test,** `scripts/qemu_app_check.py`, runs `jiro.py`'s `run()` unmodified on the qemu port, with `lcd`, `ui`, `save`, `wedgie`, `time` and `os.urandom` stubbed (the `wedgie` stub's `rand` fails, so the app cannot call it again) and the app's files in a RAM filesystem whose `open()` allocates a 1,148-byte file object, as the wedgie's does. The test's own files sit above one large free block, and a ballast fills the heap down to the given free bytes, 32 of them small holes of 64 to 512 bytes between live blocks by default (a fourth argument changes the count). At the first level select, once the app has started, the test fills every free block over 1 KB, as the wedgie's heap was after round E1's second build started, and locks the heap over each tick's sample, step and drawing, so that a tick that allocates fails. The `time` stub's `ticks_us` wraps 2³⁰ early in each level, and on tick 70 jumps 600 s ahead, past `ticks_diff`'s 2²⁹ µs range, as a wedgie whose ticks fell that far behind would see it: the build before round E1's fixes slept for minutes there, and the test's timeout failed it. Scripted keys pick level 1, play 88 ticks with two captures, a fast cut, a shield tap, and Y and the joystick press held, then commit; then back on the level select they pick level 2 and play it the same way, so that what a level allocates is allocated twice. The first `save.store` raises `OSError("flash full: ...")`, as a wedgie's does, after allocating the bests' text and a file object: the app must take its stack back and play level 2, whose store saves both bests. It checks, per level, the journal (header, and events equal to the scripted keys' mask changes), the end, claim, ticks and score against `jiro-tools replay` of that journal, the stored best, the summary screen (the first saying the best was not saved), and no overrun before the clock's jump, then one on every tick; the heap printed at each stage; and that the heap was locked over every tick. With `--hard-irq`, on the firmware `build-qemu.sh irqsim` builds, the qemu port's SysTick interrupt also calls a Python callback as a hard IRQ at every tick, as the wedgie firmware's key IRQ runs on any key press: `scripts/irqsim/`, a user C module, wraps the port's handler with `ld --wrap` and dispatches the callback with MicroPython's own `mp_irq_dispatch`, as the rp2 port's GPIO interrupt does. Every check must still pass, some of the calls must have interrupted `jiro_core` (about 47 of about 17,400 do), and none may fail; the build before round E1's third-try fix froze at the first call that interrupted the core, as the wedgie did. With `--screen` the test keeps a copy of the screen as the app's pushes leave it, and after every tick's drawing checks that the app pushed every pixel it drew, then that the app's own full redraw draws that same picture: the tick's partial drawing must leave nothing stale, in the framebuffer or on the screen. The copy takes 28,800 bytes of the port's heap, so that run gets 100,000 free bytes, and its checks run inside the app's ticks, so its times are not the app's. The test fails if the ballast did not leave the free bytes it was asked for. CI also runs it at 113,568 bytes free with 50 holes, the heap a power-up with the WEDGIE drive leaves (below). At 137,760 bytes free, the worst tick (a capture) took 1.42 million instructions, the worst step 1.29 million and the worst draw 0.16 million (with the heap locked, every frame on the C stack; unlocked, in heap layouts of 0 to 40 holes, the draw took up to 0.22 million); at 125 MHz and one instruction per cycle that is 11.4, 10.3 and 1.3 ms. The most rows pushed in a tick were 110, about 5 ms on a wedgie at 45 µs a row. The other 15 levels, played with the same inputs before the player's ring, stayed within 1.45 million instructions a tick and 136 rows. A wedgie's own numbers come from round E1 (`reports/wedgie-2026-11-02.md`).

## Installing on a wedgie

Download and unzip the `wedgie-check` or `wedgie-app` artifact of a CI run (or build it, above), and from its folder, with wedgie's CLI ([wedgie.dev/wedgie.py](https://wedgie.dev/wedgie.py)):

```bash
python3 wedgie.py install .
```

Press green on the wedgie to accept. The check app then shows its progress and results; the Training app its level select. Both are `mod` `jiro`, so installing one replaces the other. Don't run `python3 wedgie.py debug` while the check runs: it stops the app and restarts it. Run it afterwards, to read `error.log` if the app ended on an error.

**If the wedgie hangs on an app,** for example on its splash screen with USB unresponsive: unplug it, hold both grey buttons (B and X) while plugging it in, which starts it without its app, then run `python3 wedgie.py uninstall`.
